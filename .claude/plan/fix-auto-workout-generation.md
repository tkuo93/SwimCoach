# Plan: Fix Auto-Workout Generation Bug

## Problem Diagnosis

### Issue 1: Multiple workouts generated for "today's date" on every app open

**Root cause: In-memory cache is ineffective on free-tier hosting.**

The `GET /api/workouts` route in `workouts.js:96-102` fires `checkAndGenerateUpcomingWeek` via `setImmediate` on **every** request. The in-memory `lastCheckCache` (`workout-scheduler.js:24`) is supposed to prevent duplicate runs per user per target ISO week.

**However**, the app runs on Render free tier with `min_machines_running: 0` (containers sleep when idle). When the container sleeps:
1. The Node.js process dies
2. The in-memory `lastCheckCache` Map is wiped
3. The user opens the app → container wakes → new process → cache is empty
4. The scheduler runs again → generates another full week of workouts for next week

The plan doc (`auto-generate-weekly-workouts.md`) even acknowledges this design: "A per-process in-memory guard ensures we only run the check once per user per target ISO week." But this is fundamentally broken on free-tier hosting because the process restarts on every container wake.

**Current behavior**: Every app open (on a fresh process) → scheduler runs → checks next week for existing workouts → finds none → generates a full week → next app open wakes a fresh process → cache is gone → generates another full week → duplicates accumulate.

**The user says "today's date"** — this is because the scheduler targets "next week" but on the *first* day of the week (Monday), "next week" could still start on the same day the user previously generated for, and with the timezone comparison mismatch (Issue 3 below), existing workouts from the previous generation may not be detected, causing same-day duplicates.

### Issue 2: Workouts don't strictly follow the training schedule

The scheduler uses `countWorkoutsInWeek` which only counts **any** workouts in the week — it doesn't check whether workloads for specific schedule days exist. When it generates, `program-generator.js:278-283` builds `weeklyPattern` from `poolDays` and `gymDays`. If a user's profile has `poolDays: ["monday", "wednesday", "friday"]` and `gymDays: ["tuesday", "friday"]`, the pattern includes both pool and gym on Friday — that's correct (two sessions on Friday).

But the problem is: the generator **always generates the full weekly pattern** whenever the count is 0 for the target week. It doesn't consider that the user may only swim 3x/week and gym 2x/week — if the DB query returns 0 (because nothing has been generated yet for that week), it generates the full pattern. This is by design.

The real issue is the **lack of persistence of the "already generated" state**. Without a durable record of which weeks have been generated, the check always regenerates.

### Issue 3: Timezone mismatch in existing-date comparison

In `workout-scheduler.js:168`:
```js
existingDates: existingDates.map(d => d.toISOString()),
```
This produces UTC ISO strings (e.g., `"2026-06-29T00:00:00.000Z"`).

In `program-generator.js:314-316`:
```js
const existingDateKeys = new Set(
  (rest.existingDates || []).map(d => new Date(d).toLocaleDateString('en-CA'))
);
```
`toLocaleDateString('en-CA')` uses the **server's local timezone**. If the server is in UTC, `new Date("2026-06-29T00:00:00.000Z").toLocaleDateString('en-CA')` returns `"2026-06-29"`. But `nextDateForDay` (line 48-56) computes dates using `new Date()` local-time constructors. If there's any timezone discrepancy, the date keys won't match, existing workouts won't be skipped, and duplicate workouts get generated for the same day.

## Proposed Fix

### Fix 1: Replace in-memory cache with MongoDB-backed tracking

Replace the in-memory `lastCheckCache` with a persistent record. Add a `lastAutoGeneratedAt` field to `SwimmerProfile` that records when the last auto-generation happened for a given target week. This survives container restarts.

**Changes:**
- `src/models/SwimmerProfile.js`: Add `lastAutoGeneratedWeek: String` field (stores ISO week key like `"2025-W25"`)
- `src/services/workout-scheduler.js`: Replace `lastCheckCache` with a DB-backed check using `SwimmerProfile.lastAutoGeneratedWeek`

### Fix 2: Check "upcoming week" correctly — skip if already has ANY workouts for that target week

The current `countWorkoutsInWeek` counts workouts in the target week range. If > 0, it fetches dates and passes `existingDates` to skip. This is correct in principle. The bug is solely that the cache doesn't persist. With Fix 1, the DB-backed guard will prevent re-generation even after container restarts.

### Fix 3: Use UTC-consistent date comparison

Replace `toLocaleDateString('en-CA')` with a UTC-based date string comparison to avoid timezone mismatches:

```js
// Instead of: new Date(d).toLocaleDateString('en-CA')
// Use: new Date(d).toISOString().split('T')[0]  // UTC YYYY-MM-DD
```

This ensures the `existingDateKeys` set and the `nextDateForDay` results (which use `setHours(0,0,0,0)` on local time) are compared consistently. However, since both sides need to be consistent, we should standardize on UTC ISO date strings throughout.

### Fix 4: Only generate if truly missing workouts, respecting the training schedule

The scheduler should check whether the user's *schedule* days for the upcoming week have workouts, not just "any" workouts. If the user has workouts on some days but those don't match their schedule, we should still not duplicate. The current `existingDates` skip logic handles this, but only if the dates match (Fixed by Fix 3).
